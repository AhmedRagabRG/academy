Frontend API Data Requirements

Al-Salam Academy — apps/web (Next.js App Router, TypeScript, TanStack Query, Zod, RTL Arabic).

This document describes what data the existing frontend needs from the future backend. It is derived exclusively from the code in this repository: routes, screens, forms, Zod schemas, TypeScript domain types, service facade interfaces, mock services, and fixture data. It proposes the HTTP surface required to replace the in-memory mocks — it does not design the backend, its modules, its persistence, or its schema.

The single most useful fact in this document Every feature module already defines a service facade interface (for example apps/web/src/features/students/services/students-service.ts). Those interfaces are the real API contract. Each mock implementation satisfies the same interface, so replacing a mock with an HTTP client changes no screen. Every endpoint proposed below maps 1:1 to a method on one of those interfaces.

3. Global conventions

3.1 Response envelope — important mismatch to decide on

The frontend service facades today return bare payloads, not an envelope. A list method returns Paginated<T>, defined identically in six modules as: 

// apps/web/src/features/students/types/common.ts (and 5 siblings)
interface Paginated<T> {
  items: T[]
  total: number
  page: number
  pageSize: number
  totalPages: number
}

This document presents every example using the requested { success, data, meta } envelope, because a consistent envelope is the better contract for a new API. That choice requires a thin adapter in the frontend’s HTTP client. The mapping is mechanical and belongs in one place per module: 

// Recommended single adapter — the ONLY place the envelope is unwrapped.
function unwrapList<T>(body: PaginatedResponse<T>): Paginated<T> {
  return {
    items:      body.data,
    total:      body.meta.total,
    page:       body.meta.page,
    pageSize:   body.meta.limit,      // note: `limit` on the wire, `pageSize` in the app
    totalPages: body.meta.totalPages,
  }
}
function unwrap<T>(body: ApiResponse<T>): T { return body.data }
Decision required before implementation Either (a) the API emits {success,data,meta} and the frontend adds the adapter above, or (b) the API emits {items,total,page,pageSize,totalPages} directly and no adapter is needed. Option (b) is a smaller change to this frontend; option (a) is the more conventional API. This document assumes (a) and flags it as the single largest shape assumption made here.
Note also: the frontend calls the page-size field pageSize; the requested envelope calls it limit. Pick one and keep it consistent — do not let both names reach the same layer.

3.2 Pagination

  • Offset pagination on every list. Query fields the frontend produces: page (1-based) and pageSize.
  • MAX_PAGE_SIZE = 100 is enforced client-side in shared/utils/list-query.ts (clampPaging); the API must enforce the same ceiling.
  • Default page size is 20 in every module (features/student-finance/utils/finance-list-query.ts, and the equivalent per module).
  • hasNextPage / hasPreviousPage are not used anywhere in the frontend. They are safe to include but are currently dead weight; totalPages is what the pager reads.
  • Cursor pagination is used for exactly two timeline reads (Students, Student Finance) via Cursor<T> = { items: T[]; nextCursor?: string }. Those are called out in their modules.
  • The frontend clamps an out-of-range page rather than dropping filters (clampPage). The API should return an empty data array with correct meta rather than a 4xx for an over-range page.

3.3 Money — never a float

apps/web/src/shared/utils/money.ts is explicit: money is a decimal string, and every operation converts to integer minor units. The canonical shape is: 

interface Money {
  amount: string     // decimal string, e.g. "18000.00" — never a number
  currency: string   // ISO 4217, e.g. "EGP"
  precision: number  // minor-unit digits, e.g. 2
}

Every module now uses this shape. Academic Catalog previously carried { amount: number } and Program Batches omitted precision; both were corrected in the frontend — see §9.2. The API should emit the three-field decimal-string Money everywhere, including for all nine catalog pricing figures.

Seeded currency across all fixtures: EGP, precision 2.

3.4 Identifiers, dates, text

  • IDs are strings everywhere — branded string types (Brand<string,"StudentId">) that erase to string at runtime. Emit UUID strings. No numeric IDs appear anywhere in the frontend.
  • Timestamps are ISO 8601 UTC strings with milliseconds: "2026-08-01T10:00:00.000Z" (fixtures use exactly this form).
  • Calendar dates (due dates, schedule dates, birth dates) are date-only "2026-10-31". isWithinRange in shared/utils/list-query.ts treats a date-only upper bound as inclusive to the end of that day — the API must match this, or last-day rows silently vanish from queues.
  • Arabic content is primary. Labels, names, descriptions, reasons and all error messages are Arabic. Responses must be UTF-8 (Content-Type: application/json; charset=utf-8) with no escaping of Arabic codepoints.
  • Search normalization is performed client-side today (normalizeArabic: folds آأإٱ→ا, ى→ي, ة→ه, strips diacritics; normalizeDigits folds Arabic-Indic digits to ASCII). Server-side search must apply the same folding or search results will differ from what users saw against the mock.

3.5 Optimistic concurrency — expectedVersion

Almost every write command in this codebase carries expectedVersion: number, and every persisted entity carries version: number. This is not optional decoration — screens surface a dedicated “record changed, refresh” message on conflict. 

// Every mutating request body includes it:
{ "...": "...", "expectedVersion": 3 }

// On mismatch the API must return the conflict code AND the current version:
{
  "success": false,
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "تم تعديل هذا السجل بواسطة موظف آخر. حدّث الصفحة ثم أعد المحاولة.",
    "details": [{ "field": "expectedVersion", "message": "currentVersion=5" }],
    "currentVersion": 5
  }
}

currentVersion is read by FinanceErrorDetails, StudentsErrorDetails and AccountingErrorDetails. Include it as a first-class field on the error object.

3.7 Permissions — the complete catalogue

Every read and write is permission-gated. Detail responses carry a permissions object so the UI never re-derives authority (StudentAreaPermissions, FinanceAreaPermissions, ExpenseRequestPermissions, AccountingAreaPermissions). The API must compute and return these per record — an empty/absent permissions object will blank out the entire action surface of a detail page.

The authoritative key set is 125 keys granted in apps/web/src/features/auth/data/auth-fixtures.ts (mockRole.permissionKeys), checked at runtime by usePermission() in shared/hooks/use-permission.ts. Keys are namespaced module[.resource].action. Four modules also declare their keys as typed constants: features/{students,student-finance,accounting,admissions}/config/*-permissions.ts.

The permission matrix (مصفوفة الصلاحيات) now offers all 125 keys The catalogue behind /settings/permissions and /settings/roles/[roleId] used to be generated as 8 modules × 6 actions — 48 ids, of which only three matched a key the application checks, leaving Catalog, Batches, Admissions, Students, Finance and Accounting entirely ungrantable. It is now enumerated in shared/config/permission-catalog.ts and composed per module, the same way foundation-navigation.ts composes navigation. A contract test asserts the catalogue and the enforced key set agree exactly — 0 missing, 0 phantom. See §9.1.

3.7.2 Separation-of-duty keys — do not collapse these

Several keys look mergeable but exist specifically to split authority. Collapsing them in the API would silently remove a financial control that the code documents as deliberate:

finance.payments.record vs finance.refunds.approve vs finance.discounts.approve vs finance.scholarships.approve“The person requesting money back is not necessarily the one authorizing it.” The separation “is the module’s main internal financial control and only means anything if the keys are distinct.”
accounting.requests.submit / .review / .decide / .markPaid / .cancel“An Executive Manager holds every read key and no decision key, which is what makes ‘visibility without participation’ enforceable rather than a UI convention.” Marking paid carries its own authority, distinct from approving.

3.8 Branch scoping

EmployeeContext carries authorizedBranchIds and organizationWide. Every list endpoint must filter to the caller’s authorized branches, and every detail endpoint must refuse an out-of-scope record with a distinct code (out-of-scope) — not a generic 403 — because the UI shows a different message for “exists but not yours”.

3.9 Standard error envelope

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "توجد بيانات غير صالحة. راجع الحقول المميزة.",
    "details": [
      { "field": "identity.primaryPhone", "message": "صيغة رقم الهاتف غير صحيحة" }
    ]
  }
}
  • details[].field must use dot paths matching the form field names (identity.primaryPhone, pricing.basePrice.amount), because forms map them straight onto React Hook Form paths.
  • Each module has a closed union of error codes with a pre-written Arabic message — see §8. The frontend never parses prose; it switches on the code.
  • Retryable codes are marked per module (e.g. service-unavailable); the UI shows a Retry button only for those.

3.10 Loading, empty and error states

Each module has an area-state wrapper (FinanceAreaState, StudentAreaState, AccountingAreaState) handling loading / error / forbidden / empty. Two API behaviours matter:

  • “No records” is a fact, not a zero. AccountingDashboard.hasNoRecords and StudentFinancialProfile.hasNoRecords exist so the UI never renders “0 EGP” when it means “nothing recorded yet”. The API must set these booleans explicitly.
  • Unavailable is not zero either. StudentFinancialSummaryResult is a discriminated union — {state:"available",summary} | {state:"unavailable",reason} | {state:"forbidden"}. Never substitute zeros for a failed finance lookup.

type BatchStatus   = "draft" | "registration-open" | "registration-closed"

interface ProgramBatch {
  id: string

  capacity: BatchCapacity
  financialProfile: FinancialProfile

  version: number

  updatedAt: string; updatedBy: string
}

interface BatchSchedule {               // all optional; ordering rules enforced across them

  studyStartDate?: string
  studyEndDate?: string
  graduationDate?: string
}

interface BatchCapacity {
  maximumStudents: number               // client-editable

}

  id: string; revisionNumber: number

  sourceBatchVersion: number
}
interface LifecycleEvent {

Purpose
Invoicing, installment plans, payments, discounts, scholarships, adjustments and refunds for enrolled students.
Actions
Raise invoices · Edit draft · Issue · Cancel · Generate installment plan · Record payment · Apply discount · Award scholarship · Request/approve/reject/complete refund · Export
Three operations that must NOT exist
  • No delete on any entity — cancellation and status changes are the only reversals.
  • No update or delete on a Payment — corrections go through a refund.
  • No write to issuedSnapshot — post-issuance reductions become FinancialAdjustment records instead.
A contract test asserts this surface. Do not add PATCH /payments/:id or any delete route.

Main object shapes

type InvoiceStatus     = "draft" | "issued" | "partially-paid" | "paid" | "cancelled"
type InstallmentStatus = "pending" | "partially-paid" | "paid" | "overdue"
type RefundStatus      = "requested" | "approved" | "completed" | "rejected" | "cancelled"
type FinancialStatus   = "no-outstanding-balance" | "partial-balance" | "overdue" | "completed"
type ReductionKind     = "percentage" | "amount"
type ScholarshipCoverage = "full-tuition" | "partial-tuition"
type ScheduleBasis     = "monthly" | "custom"

What is derived and must never be stored or accepted from a client finalAmount (after adjustments), netPaid, remaining, Installment.paidAmount, Installment.status, and the partially-paid/paid invoice statuses. utils/finance-balance.ts computes all of them from records on demand — “nothing here is stored… there is no second source of truth that can drift”. Only completed refunds reduce netPaid. Cancelled invoices stop contributing to balances but remain readable.

Installment plan — validation

{ "count": 3, "scheduleBasis": "monthly", "firstDueDate": "2026-08-24",
  "customDueDates": ["2026-08-24", "2026-09-24", "2026-10-24"], "expectedVersion": 3 }
  • count integer, 1 … installmentEligibility[offeringKind].maxCount — "عدد الأقساط يجب أن يكون بين ١ و N"
  • allowsPlan === false for the offering kind → installments-not-permitted — "هذا النوع من المنتجات لا يسمح بخطط التقسيط"
  • Any installment already carries a payment → plan-has-payments — "لا يمكن إعادة إنشاء الخطة بعد تسجيل مدفوعات على أحد الأقساط"
  • Amounts are split with allocate(): equal parts with the remainder on the last installment, and the sum must equal the total exactly.

// Each module already owns an error class. The HTTP client maps the wire error

function toStudentsError(body: ApiErrorResponse): StudentsError {
  return new StudentsError(
    body.error.code as StudentsErrorCode,
    {
      currentVersion: body.error.currentVersion,
      fieldErrors: Object.fromEntries(
        (body.error.details ?? [])
          .filter((d) => d.field)
          .map((d) => [d.field!, d.message])
      ),

9.16 Batch installment plans were balanced with float arithmetic and an epsilon fixed in the frontend

File
features/program-batches/utils/batch-money.ts (found while fixing §9.2)
// WAS
export function planTotal(plan: InstallmentPlan) {
  return plan.installments.reduce((sum, item) => sum + Number(item.value), 0)
}
export function coveredAmount(profile: FinancialProfile, plan: InstallmentPlan) {
  const price = Number(profile.programPrice.amount),
    fee = Number(profile.registrationFee.amount)
  return plan.coveredCharge === "program-price" ? price
    : plan.coveredCharge === "registration-fee" ? fee : price + fee
}
export function isPlanBalanced(profile: FinancialProfile, plan: InstallmentPlan) {
  const expected = plan.basis === "percentage" ? 100 : coveredAmount(profile, plan)
  return Math.abs(planTotal(plan) - expected) < 0.01     // ⚠ epsilon
}

Why it broke. Two problems, one hiding the other. Every amount was read through Number(...), so an installment schedule was summed in binary floating point — the drift shared/utils/money.ts exists to prevent. The < 0.01 tolerance then absorbed that drift, but it also silently accepted a plan that was genuinely up to a whole minor unit short of the charge it covers. On a schedule shown to a student that is a real discrepancy, not a rounding artifact. The epsilon was the symptom, not the fix.

Resolved — exact comparison in integer minor units planTotal and coveredAmount now return Money and use sum/add; isPlanBalanced uses compare(...) === 0. Percentage plans are summed as integers scaled to two decimals, so 33.33 + 33.33 + 33.34 resolves to exactly 100 — which it does not as floats. A plan is balanced or it is not; there is no tolerance.

For the API: the same rule applies server-side. An installment plan whose parts do not sum exactly to the covered charge must be refused, not accepted within a tolerance. This mirrors allocate() in Student Finance, which already asserts an exact split.

10. Assumptions made in this document

Everything below is a choice this document made that the frontend does not determine. Each is reversible; none affects the data shapes themselves.

  1. Response envelope. Examples use {success, data, meta} as requested. The frontend natively expects bare payloads and {items,total,page,pageSize,totalPages}. §3.1 gives the exact adapter. This is the single largest assumption.
  2. limit vs pageSize. The envelope’s meta.limit is the frontend’s pageSize. Query examples use page/pageSize since that is what the client constructs.
  3. sortBy/sortOrder naming. Query examples use these names as requested; the frontend types call them sort/direction (or a structured sort:{field,direction}). Mechanical rename at the client.
  4. URL prefix /api/v1 and path spellings. No base URL, route constant or HTTP client exists anywhere in the codebase — there is no fetch or axios call to constrain this. Paths were derived from the service method names and route structure.
  5. HTTP verbs and status codes. Chosen conventionally. The frontend switches on error codes, not status numbers, so status choices are low-risk.
  6. File uploads use multipart/form-data with field name file. The mocks pass file metadata objects (DocumentFileInput) or a File; the wire format is undetermined by the code.
  7. A generic POST /api/v1/files/upload. Inferred from FileAsset, CatalogAsset and profileImageUrl existing on entities with no upload endpoint in any facade. Marked as new.
  8. GET /api/v1/finance/dashboard/summary. No longer an assumption — it now exists on StudentFinanceService as getDashboardSummary(), added to fix the capped-page bug in §9.11. Only its URL and verb are chosen here.
  9. Auth transport. Session cookie vs bearer token is not determined by the code; the mock uses localStorage. GET /auth/session is specified to return data: null rather than 401, because the facade is typed Promise<EmployeeContext | null>.
  10. Cursor format. Opaque strings. The frontend only round-trips nextCursor; the code reveals only that sequence participates in ordering.
  11. Server-side Arabic search folding. Assumed to mirror normalizeArabic / normalizeDigits. Not currently a server concern because search is in-memory.
  12. Uniqueness scopes. Product code, branch code, user email, category name assumed unique per organization; sub-category name unique within its parent (this last one is explicit in the code).
  13. Error codes for the four older modules. Settings, Catalog, Batches and Admissions use free-form code strings; the specific codes listed for them (DUPLICATE_CODE, NOT_READY, DEPENDENCY_IN_USE, …) are proposed, not extracted. Students, Finance and Accounting codes are verbatim from the code.
  14. Arabic error copy for proposed codes. Where a module has no existing message (e.g. ACCOUNT_INACTIVE), the Arabic text shown is suggested, not extracted.
  15. Sortable columns for Settings entities. Inferred from the table columns; ListQuery.sort is typed as an unconstrained string.
  16. Example values. IDs, invoice numbers, references and dates in the examples are illustrative and consistent with the fixtures, not extracted records.
